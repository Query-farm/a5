## Project Overview

This is a DuckDB extension that provides A5 geospatial indexing functions. A5 is a pentagonal geospatial index system with millimeter-accurate, equal-area cells across 31 resolution levels.

**Architecture**: The extension uses a hybrid C++/Rust implementation:
- **Rust core** (`a5_rust/`): Provides FFI bindings to the upstream `a5` crate (v1.0.0)
- **C++ wrapper** (`src/`): Implements DuckDB scalar functions that call into Rust via C FFI
- **Build system**: CMake with Corrosion for Rust integration

## Architecture Details

### FFI Layer (Rust ↔ C++)

The Rust FFI bindings are in `a5_rust/src/lib.rs`. Key patterns:

1. **Error handling**: Rust functions return C-compatible structs (`ResultU64`, `ResultF64`, `ResultBool`, `ResultLonLat`) with nullable error pointers
2. **Memory management**: Array returns (`LonLatDegreesArray`, `CellArray`) transfer ownership to C++; must be freed with `a5_free_*` functions
3. **Generated header**: `src/include/rust.h` is generated by cbindgen, but **not** automatically during the build. After changing FFI signatures in `a5_rust/src/lib.rs`, regenerate and commit it manually:
   ```bash
   cd a5_rust && cbindgen --config cbindgen.toml --lang c++ --output ../src/include/rust.h src/lib.rs
   ```
   (The committed header is C++-style; pass `--lang c++` so the diff stays clean.)

### C++ DuckDB Integration

`src/a5_extension.cpp` implements scalar functions using DuckDB's executor framework:
- `UnaryExecutor`: Single input parameter (e.g., `a5_cell_area`, `a5_get_resolution`)
- `BinaryExecutor`: Two input parameters (e.g., `a5_cell_to_parent`)
- `TernaryExecutor`: Three input parameters (e.g., `a5_lonlat_to_cell`)
- Manual loops for array outputs (e.g., `a5_cell_to_boundary`, `a5_cell_to_children`)

All functions validate that resolution parameters are ≤30 (MAX_RESOLUTION constant). Where the crate accepts `-1` (the world cell) as a coarser resolution — `a5_cell_to_parent`, `a5_cell_to_supercell`, `a5_get_num_children`, `a5_cell_area` — so does the SQL function (`ValidateResolutionOrWorld`).

### GEOMETRY Integration

Several functions consume or produce DuckDB's built-in `GEOMETRY` type (`LogicalType::GEOMETRY()`), which requires **no** dependency on the `spatial` extension. DuckDB stores `GEOMETRY` as plain little-endian ISO WKB, so the extension parses/emits WKB directly in `src/a5_extension.cpp`:
- `a5_geometry_to_cells` parses any geometry (POINT/LINESTRING/POLYGON, MULTI*, GEOMETRYCOLLECTION) via a recursive WKB reader; polygon holes are excluded by the a5 crate itself. A geometry with polygon parts is returned as a single covering (see below); point/line-only geometries keep their cells uncompacted, in geometry order.
- `a5_cell_to_geometry` / `a5_cell_to_point` build WKB `POLYGON`/`POINT` values.

The Rust FFI functions `a5_line_string_to_cells` / `a5_polygon_to_cells` are **internal-only** — called by the WKB reader, not registered as DuckDB functions.

### A5 1.0: cell index and coverings

- **Cell IDs changed in a5 1.0** (the "v1 index"). IDs produced by a5 <= 0.10 name the same cells but have different values; `a5_migrate` converts them. Expected cell IDs in tests are v1 values.
- **Coverings**: `a5_compact`, `a5_grid_disk`, `a5_grid_disk_vertex`, `a5_spherical_cap`, `a5_cell_to_subcells`, `a5_union` / `a5_intersect` / `a5_difference` and polygon results of `a5_geometry_to_cells` return compacted cells sorted in curve order **followed by a compaction marker** — a `UBIGINT` that is not a cell and records the resolution the cells stand for. The marker is passed through to SQL unchanged so that `a5_uncompact(cells)` and the set operations know the resolution; `a5_is_compaction_marker` identifies it.
- `a5_uncompact(cells)` expands to the covering's own resolution, as upstream does; the pre-1.0 `a5_uncompact(cells, target_resolution)` form was removed (1.0 is a breaking release — user-facing changes are listed in `docs/UPGRADING.md`). The README is intentionally minimal; the full function reference lives at https://query.farm/products/extensions/a5 and must be updated there.
- Only the crate's top-level re-exports (`a5::*`) are supported API; `a5::core::*` etc. are `#[doc(hidden)]` — do not reach into them.

### Build System

CMake configuration (`CMakeLists.txt`) handles:
- Platform-specific Rust target detection (macOS: aarch64/x86_64-apple-darwin, Linux: gnu/musl, Windows: gnu/msvc)
- Corrosion integration (v0.5.2) for Rust compilation
- Links `a5_rust-static` (static extension) or `a5_rust` (loadable extension)

The extension uses DuckDB's extension-ci-tools (git submodule) for standardized build infrastructure.

## Development Workflows

### Adding New A5 Functions

1. Add Rust FFI binding in `a5_rust/src/lib.rs`:
   - Use `#[no_mangle] pub extern "C"` for function signature
   - Return C-compatible result types
   - Handle Result<T, E> from upstream `a5` crate

2. Regenerate the C header manually (cbindgen is **not** wired into the build):
   `cd a5_rust && cbindgen --config cbindgen.toml --lang c++ --output ../src/include/rust.h src/lib.rs`

3. Implement DuckDB function in `src/a5_extension.cpp`:
   - Choose appropriate executor (Unary/Binary/Ternary)
   - Add input validation
   - Register in `A5Extension::Load()` via `CreateScalarFunctionInfo`

4. Add tests in `test/sql/a5.test` (SQLLogicTest format)

The SQL surface should mirror the crate's public API (the `pub use` list in its `lib.rs`) as closely as possible: same names with an `a5_` prefix, same optional arguments, same results. Wrap every fallible crate call in `guard(...)` in `a5_rust/src/lib.rs` so a panic inside the crate becomes a SQL error instead of aborting DuckDB.

### Working with Rust Dependencies

- Update `a5` crate version in `a5_rust/Cargo.toml`
- Run `cargo update` in `a5_rust/` directory
- Rebuild with `make clean && make debug`

### Platform-Specific Builds

The build system auto-detects Rust targets. For cross-compilation, set `OSX_BUILD_ARCH` (macOS) or use appropriate `DUCKDB_PLATFORM` values:
```bash
# macOS ARM64
make release OSX_BUILD_ARCH=arm64

# macOS x86_64
make release OSX_BUILD_ARCH=x86_64
```
